Use this page when a user reports a failed deposit, withdrawal, account registration, or order request and the root cause is not yet clear. The key first step is to determine whether the failure happened on-chain (a blockchain transaction was submitted but reverted or was never confirmed) or at the API level (the LiqZero backend rejected the request before any on-chain action was taken). The two failure types have different diagnostic paths.

## Step 1 — Identify the Failure Type

Before looking at error details, collect the following context from the user:

- **Wallet address** and **broker/builder ID**
- **Chain** the action was attempted on
- **Market symbol** (if an order failure), e.g., `PERP_ETH_USDC`
- **Timestamp** of the failure
- **Transaction hash** (if the failure is on-chain)
- **Order ID** or **API error response** (if the failure is an API rejection)

Once you have this information, determine which category applies:

| Failure type | Indicator |
|---|---|
| On-chain transaction failure | A transaction hash exists but the tx was reverted or is stuck |
| API-level failure | An HTTP response with a non-200 status code or a JSON error body |
| Order rejection | An HTTP 400 response with a negative error code in the `code` field |

## On-Chain Transaction Failures

<Accordion title="Check the transaction on a block explorer">
  Navigate to the block explorer for the relevant chain and look up the transaction hash. The table below lists the explorers for LiqZero's supported chains:

  | Chain | Explorer |
  |---|---|
  | Arbitrum | arbiscan.io |
  | Optimism | optimistic.etherscan.io |
  | Base | basescan.org |
  | Ethereum | etherscan.io |
  | Avalanche | snowtrace.io |
  | BNB Smart Chain | bscscan.com |
  | Mantle | explorer.mantle.xyz |
  | Sonic | sonicscan.org |
  | SEI | seitrace.com |

  Look for one of the following:

  - **Status: Failed / Reverted** — The transaction was submitted but the smart contract rejected it. Expand the transaction details to find the revert reason string.
  - **Status: Pending** for more than 10 minutes — The transaction may have insufficient gas or the network may be congested. The user may need to speed up or resubmit the transaction.
  - **Not found** — The transaction was never broadcast. The user's wallet may have dropped it before submission.
</Accordion>

<Accordion title="Common on-chain revert reasons">
  | Revert reason | Likely cause | Resolution |
  |---|---|---|
  | `insufficient allowance` | The user did not approve enough USDC for the Vault contract | Ask the user to approve the correct token amount before depositing |
  | `wrong token` | The user attempted to deposit a non-USDC token | Only USDC deposits are supported |
  | `invalid account id` | The account ID in the calldata does not match the wallet | Verify the account ID was computed correctly from the wallet address and broker ID |
  | `paused` | The contract is in maintenance mode | Check the [API status and maintenance information](/api-reference/introduction) and notify users |
  | Out of gas | Gas limit was set too low | Ask the user to retry with a higher gas limit |

  <Warning>
    Always verify that the user is interacting with the **official LiqZero contract addresses** for the relevant chain. Transactions sent to unofficial or outdated contract addresses will fail. See [Smart Contract Addresses](/api-reference/contracts/addresses) for the current address list.
  </Warning>
</Accordion>

## API-Level Failures

<Accordion title="Check the HTTP status code and response body">
  LiqZero API responses include an HTTP status code and, for errors, a JSON body with `success: false`, a `code` field, and a `message` field:

  ```json
  {
    "success": false,
    "code": -1103,
    "message": "Order price does not match the tick size."
  }
  ```

  Start by checking:
  1. **HTTP status code** — `400` for validation/order errors, `401` for authentication failures, `429` for rate limiting.
  2. **`code` field** — Use the table below to map to the exact failure reason.
  3. **`message` field** — Contains a human-readable description of the specific constraint that was violated.
</Accordion>

<Accordion title="Diagnose authentication failures (-1001, -1002)">
  Authentication failures occur when one or more of the four required request headers is missing, malformed, or invalid.

  | Header | What to check |
  |---|---|
  | `perpo-timestamp` | Must be within **±5 seconds** of current UTC time. Clock drift is the most common cause of auth failures. |
  | `perpo-key` | Must be formatted as `ed25519:<base58-public-key>`. The key must be currently registered and not expired. |
  | `perpo-signature` | Must be computed by signing the canonical message string (timestamp + method + path + body) with the ed25519 private key. |
  | `perpo-account-id` | Must match the account ID derived from the wallet address and broker ID used during registration. |

  See the [API Authentication guide](/api-reference/authentication) for the exact signature construction algorithm.
</Accordion>

<Accordion title="Diagnose rate limiting (-1003)">
  Error `-1003` means the request rate limit has been exceeded. LiqZero enforces per-account and per-IP rate limits on API endpoints.

  - Implement exponential backoff with jitter in your retry logic.
  - Cache market data responses where possible instead of polling every endpoint at the maximum rate.
  - WebSocket subscriptions are more efficient than polling REST endpoints for live data — switch to the [WebSocket API](/api-reference/websocket/introduction) for orderbook and trade streams.
</Accordion>

## Order Rejection Error Codes

Use the accordions below to diagnose specific order rejection codes.

<Accordion title="-1101 — Risk exposure too high / insufficient margin">
  The order was rejected because placing it would cause the account's risk exposure to exceed the allowed threshold, or there is insufficient free margin to support the position.

  **Diagnostic steps:**
  1. Call `GET /v1/client/info` with the user's account to retrieve their current `total_collateral_value`, `free_collateral`, and `max_notional`.
  2. Confirm the order's notional value (price × quantity) does not exceed the remaining available exposure.
  3. Check the account's current leverage setting — a lower leverage setting reduces the maximum position size.
  4. Ask the user to deposit more collateral or reduce their open positions before retrying.
</Accordion>

<Accordion title="-1102 — Order value too small">
  The order's notional value (price × quantity) is below the symbol's minimum order value.

  **Diagnostic steps:**
  1. Call `GET /v1/public/info` and find the `min_notional` field for the relevant symbol.
  2. Ensure the order's price × quantity exceeds this value.
  3. Adjust the order size upward or use a market order at a price closer to mid to increase notional.
</Accordion>

<Accordion title="-1103 — Price out of range or invalid tick size">
  The order price is either below `quote_min`, above `quote_max`, or does not conform to the symbol's tick size (smallest allowed price increment).

  **Diagnostic steps:**
  1. Retrieve symbol info via `GET /v1/public/info` and check `quote_min`, `quote_max`, and `quote_tick`.
  2. Ensure the submitted price falls within `[quote_min, quote_max]`.
  3. Round the price to the nearest multiple of `quote_tick` before submitting.
</Accordion>

<Accordion title="-1104 — Quantity out of range or invalid step size">
  The order quantity is either below `base_min`, above `base_max`, or does not conform to the symbol's step size (smallest allowed quantity increment).

  **Diagnostic steps:**
  1. Retrieve symbol info via `GET /v1/public/info` and check `base_min`, `base_max`, and `base_tick`.
  2. Ensure the submitted quantity falls within `[base_min, base_max]`.
  3. Round the quantity to the nearest multiple of `base_tick` before submitting.
  4. If you're using `visible_quantity` for an iceberg order, ensure it also conforms to `base_tick`.
</Accordion>

<Accordion title="-1105 — Price too far from mid price">
  The limit order price is too far from the current mid price. LiqZero enforces a maximum deviation to protect against fat-finger errors and extreme order placement.

  **Diagnostic steps:**
  1. Retrieve the current mid price from the orderbook via WebSocket or `GET /v1/public/market_trades`.
  2. Ensure your limit price is within the allowed deviation band.
  3. If the user intends to place a wide limit order, use a stop-limit order type instead.
</Accordion>

<Accordion title="-1011 — Internal network error (retry)">
  A transient internal error occurred while processing the order. This is not caused by the order payload.

  **Resolution:** Retry the exact same request after 1–5 seconds. If the error persists beyond three retries, collect the request payload and timestamp and escalate to support.
</Accordion>

<Accordion title="-1012 — Account in liquidation">
  The account is currently being liquidated. No new orders can be placed while a liquidation is in progress.

  **Resolution:** Wait for the liquidation process to complete. The user's positions will be reduced to bring the account above the maintenance margin threshold. Once liquidation is finished, trading resumes normally.
</Accordion>

## Escalating to Support

If you have completed the steps above and the issue remains unresolved, submit a ticket in the [LiqZero Discord](https://discord.gg/OrderlyNetwork) with:

- Wallet address and broker ID
- Chain, market symbol, and timestamp
- Full API request payload (redact the private key)
- Full API response body
- Transaction hash (if applicable)
