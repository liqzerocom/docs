LiqZero uses a set of audited smart contracts deployed on every supported chain to act as the on-chain custody and messaging layer for your DEX. Your users never hand funds directly to an off-chain system — they interact with a Vault contract on their preferred chain, which holds their USDC and communicates deposit and withdrawal events to the LiqZero L2 settlement layer. Your integration calls the REST and WebSocket APIs to manage orders and positions; the contracts handle the asset custody and cross-chain coordination autonomously.

## Architecture at a Glance

The LiqZero contract system has three logical layers:

<CardGroup cols={3}>
  <Card title="Vault Contracts" icon="vault">
    Deployed on every supported EVM chain and Solana. Holds user USDC deposits and processes withdrawal requests. The canonical entry point for user funds.
  </Card>
  <Card title="Cross-Chain Relay" icon="network-wired">
    Uses LayerZero messaging to relay deposit confirmations and withdrawal instructions between the Vault on each chain and the LiqZero L2 settlement layer (Chain ID 291).
  </Card>
  <Card title="Ledger / Settlement Layer" icon="file-invoice-dollar">
    Deployed on LiqZero L2. Maintains the canonical ledger of balances, positions, and PnL. The EIP-712 verifying contract for withdrawal messages lives here.
  </Card>
</CardGroup>

## Deposit Flow

When a user deposits USDC, the following sequence occurs:

<Steps>
  <Step title="Approve USDC spending">
    The user calls `approve` on the USDC contract, authorising the Vault contract to transfer the deposit amount on their behalf.
  </Step>
  <Step title="Call deposit on the Vault">
    Your integration calls `deposit(DepositData)` on the chain's Vault contract. The function transfers USDC from the user's wallet into the Vault and emits a deposit event.
  </Step>
  <Step title="Get the cross-chain fee">
    Before calling `deposit`, call `getDepositFee()` on the Vault to retrieve the native-token fee required to pay for the LayerZero cross-chain message. Pass this value as `msg.value` in the `deposit` call.
  </Step>
  <Step title="LayerZero relays the message">
    The Vault's `CrossChainRelay` contract sends a LayerZero message to the LiqZero L2 Ledger, confirming the deposit amount and crediting the user's trading balance.
  </Step>
  <Step title="Balance available for trading">
    Once the L2 Ledger processes the cross-chain message, the user's LiqZero account balance increases and they can place orders immediately.
  </Step>
</Steps>

## DepositData Struct

The `deposit` function accepts a single `DepositData` struct. Construct this on the client side before calling the contract:

```solidity DepositData struct
struct DepositData {
    bytes32 accountId;   // Your user's LiqZero account ID (32-byte padded)
    bytes32 brokerHash;  // keccak256(abi.encodePacked(brokerId)) — your broker identifier
    bytes32 tokenHash;   // keccak256(abi.encodePacked("USDC"))
    uint128 tokenAmount; // Deposit amount in USDC's native decimals (6 decimals)
}
```

<Note>
`tokenAmount` is denominated in USDC's raw units (6 decimal places). To deposit 100 USDC, pass `100_000_000` (100 × 10⁶). Always call `getDepositFee()` first and include the returned value as `msg.value` — failing to do so will cause the deposit transaction to revert.
</Note>

## Key Contract Functions

<Accordion title="deposit(DepositData calldata data) payable">
  **Vault contract.** Transfers `data.tokenAmount` of USDC from `msg.sender` to the Vault, then dispatches a LayerZero cross-chain message to credit the user's LiqZero account. Requires `msg.value >= getDepositFee()`.

  ```solidity
  function deposit(DepositData calldata data) external payable;
  ```
</Accordion>

<Accordion title="getDepositFee() view returns (uint256)">
  **Vault contract.** Returns the current native-token fee (in wei) required to cover the LayerZero messaging cost for one deposit. This value fluctuates with gas prices on the destination chain — always call this immediately before constructing the deposit transaction.

  ```solidity
  function getDepositFee() external view returns (uint256 fee);
  ```
</Accordion>

<Accordion title="Withdrawal — API-initiated">
  Withdrawals are initiated through the REST API, not directly by calling a contract. Your user signs an EIP-712 withdrawal message with their wallet, you submit it via `POST /v1/withdraw_request`, and the LiqZero L2 Ledger validates the signature and instructs the target chain's Vault to release funds. The Vault then transfers USDC back to the user's wallet.
</Accordion>

## Withdrawal Flow

<Steps>
  <Step title="User signs an EIP-712 message">
    Your UI prompts the user to sign a structured withdrawal message using their connected wallet. The message includes the withdrawal amount, target chain, and a nonce.
  </Step>
  <Step title="Submit via REST API">
    Your backend posts the signed message to `POST https://api.liqzero.com/v1/withdraw_request`. LiqZero validates the signature against the user's registered address.
  </Step>
  <Step title="L2 Ledger processes the request">
    The LiqZero L2 Ledger verifies the EIP-712 signature using the on-chain Ledger (Verifier) contract and deducts the amount from the user's trading balance.
  </Step>
  <Step title="LayerZero relays the release instruction">
    The LedgerCrossChainRelay sends a LayerZero message to the target chain's Vault, instructing it to release the USDC to the user's wallet address.
  </Step>
  <Step title="USDC arrives in user's wallet">
    The Vault on the target chain transfers USDC to the user's wallet. The user can subscribe to the `wallet` WebSocket topic to receive a real-time notification when the funds arrive.
  </Step>
</Steps>

## Settle PnL Flow

Unrealised PnL from perpetual positions is settled periodically. When a user requests PnL settlement, the LiqZero L2 contract adjusts their USDC balance by the net PnL amount. Settlement does not require an on-chain transaction from the user — it is handled via the `POST /v1/settle_pnl` REST endpoint, which triggers on-chain settlement via the Ledger contract.

## Trade Flow

Order matching and position management happen entirely off-chain within LiqZero's matching engine. Smart contracts are not involved in the order placement or fill process — they only custody the collateral that backs positions. This design delivers CEX-level matching performance with on-chain asset custody guarantees.

## Security and Audits

All LiqZero vault and settlement contracts are fully audited. Audit reports are publicly available at [github.com/OrderlyNetwork/Audits](https://github.com/OrderlyNetwork/Audits). All contracts are verified on their respective chain explorers — you can read the ABI and source code directly. The latest contract ABI files are published on [GitHub](https://github.com/OrderlyNetwork/contract-evm-abi).

<Warning>
Never integrate against unverified contract addresses. Always cross-reference addresses from the official [Contract Addresses](/api-reference/contracts/addresses) page before sending user funds. Do not rely on addresses obtained from third-party sources.
</Warning>

## Cross-Chain Messaging

LiqZero uses [LayerZero](https://layerzero.network/) as its cross-chain messaging protocol. Each supported chain has a `CrossChainRelay` contract that sends and receives LayerZero messages to and from the LiqZero L2 settlement layer. The relay is permissioned — only the Vault and VaultCrossChainManager contracts can dispatch messages through it.
